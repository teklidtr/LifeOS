# LifeOS Design Decisions

These are accepted architectural decisions unless a later approved decision supersedes them.

## DD-001: Markdown remains canonical

Canonical content stays in Markdown inside the vault.

## DD-002: Deterministic facts and semantic interpretation are separate

Scripts establish hashes, identity, ownership, indexes, validation, and patch application. Agents interpret meaning and create proposals.

## DD-003: Durable proposal mode

Consequential edits are represented as durable proposals with exact patches and reasons.

## DD-004: Proposal application is explicit

A deterministic command applies only explicitly approved proposal items.

## DD-005: Status and confidence

```yaml
status: seed | active | needs-review | archived
confidence: low | medium | high
review_reasons: []
```

`stale` and `contradicted` are review reasons, not exclusive statuses.

## DD-006: Stable IDs are selective

Use stable IDs for durable wiki concepts, patterns, goals, plans, experiments, metrics, sources, and policies. Do not require them for daily notes, scratch notes, raw imports, or ordinary attachments.

## DD-007: Native Obsidian references first

Use Obsidian links, headings, block references, and PDF page references internally. Portable exports may translate them.

## DD-008: Description is the lightweight summary field

Use concise `description` fields for indexes, routing, previews, dashboards, and graph nodes.

## DD-009: Managed blocks

Shared files use explicit managed-block markers. Agents may modify only inside valid blocks.

## DD-010: Explicit instruction allowlist

A future `system/instructions.yml` is authoritative. Frontmatter alone does not grant instruction authority.

## DD-011: Read before write

Every editing workflow must read the current target and applicable policy before proposing a change.

## DD-012: Preservation checks are scripted

Deterministic validators reject destructive patches that remove stable IDs, citations, user-owned sections, required headings, or approved evidence.

## DD-013: Indexes are generated by scripts

Indexes are deterministic, grouped from child metadata, and use descriptions. Folder purpose pages supply directory descriptions.

## DD-014: Context packs use multiple retrieval modes

Combine routing, lexical search, optional semantic search, graph traversal, and recent context.

## DD-015: Knowledge gaps use evidence signals

Do not fabricate numerical model confidence. Report coverage and confidence using source diversity, contradictions, freshness, and directness.

## DD-016: Adversarial review is selective

Review factual claims and aggressively challenge agent-generated personal interpretations. Do not challenge subjective journal statements. Reviewer comments do not silently edit content.

## DD-017: Original sources remain immutable

Sanitized and extracted forms are sidecars. Originals are preserved.

## DD-018: Graphify is a helper, not authority

Use Graphify behind a LifeOS relationship-graph skill. It writes only under `.lifeos/graphify/`, uses separate views, and cannot promote inferred edges into truth.

## DD-019: Graph updates are incremental

Perform one full build per graph view, then re-extract changed files. Recompute inexpensive global analysis when necessary.

## DD-020: Separate graph layers

Keep structural, inferred, learning, and analysis data separate.

## DD-021: Adaptive planning, not conventional task management

LifeOS uses rolling-wave planning and daily menus matched to current capacity.

## DD-022: Goals are directions

Long-term goals remain broad. Medium-term plans define outcomes. Only near-term work becomes small actions.

## DD-023: Tasks stay with plans

Tasks live in relevant plan files and are globally indexed by deterministic scripts.

## DD-024: Flashcards are workload sessions

Do not create one task per card. Create review workloads from due cards, estimated time, and topic.

## DD-025: Energy and motivation are distinct

Planning distinguishes capacity from pull.

## DD-026: Exercise, diet, and hobbies are not merely productivity inputs

Use strong signals such as sleep, soreness, available time, and explicit experiments. Treat weak correlations cautiously. Hobbies are legitimate activities.

## DD-027: Skipped tasks trigger diagnosis

Repeated avoidance leads to decomposition, reframing, pausing, or goal review rather than endless rescheduling.

## DD-028: Metric definitions act like data types

Canonical metric pages define valid values, units, aggregation, and missing-value behavior.

## DD-029: Optional purpose-specific exports

Do not maintain a normalized mirror. Generate exports only for concrete consumers.

## DD-030: Scope-local logs are generated views

Human-readable logs are generated from registry events rather than manually appended by every skill.

## DD-031: Git-tracked proposals and stable layout

Proposals live in stable Git-tracked folders under `proposals/<proposal-id>/`. The lifecycle state is stored strictly in the `proposal.md` frontmatter, rather than moving folders between lifecycle directories.

## DD-032: Typed JSON patches

Patches are recorded in `patches.json` using explicit, typed JSON operations (e.g., `replace_managed_block`, `patch_human_file`) with explicit target and base hashes. Raw unified diffs are not used as the sole proposal format.

## DD-033: SQLite disposability and rebuilding

SQLite is a disposable, rebuildable query state and must not be the only home of proposal history. The proposal index in SQLite must be entirely rebuildable from the Git-tracked `proposals/` files.

## DD-034: Proposal validation

`validation.json` is derived and should normally live under `.lifeos/proposal-validation/`, not as canonical proposal history. Furthermore, approval does not bypass application-time validation; an approved proposal whose targets changed must be refused as stale.

## DD-035: Durable generated ownership

Generated ownership is durable authorization data. `system/generated-ownership.json` is the canonical Git-tracked location. The disposable `.lifeos/` directory must never contain the only ownership record. SQLite may index ownership but is not authoritative, and deleting SQLite must not affect ownership. Git rollback restores generated files and their ownership metadata together. Generated-file application must eventually update file content and ownership atomically. A missing canonical manifest causes proposal preflight to fail closed. The manifest cannot currently be reconstructed because generated files do not independently declare generator identity.

## DD-036: Obsidian is the primary interface and Python is the sole business-rule engine

The desktop plugin is a thin TypeScript client. It must not reimplement planning, study,
attention, proposal, recovery, status, or canonical mutation semantics.

## DD-037: The default desktop transport is a vault-scoped STDIO child process

The plugin launches one local Python bridge per vault and communicates using versioned
newline-delimited JSON-RPC over dedicated STDIO. Logs use files, never protocol STDOUT. A
background service is optional and reserved for scheduled attention while Obsidian is closed.

## DD-038: Direct UI writes use optimistic concurrency and idempotency

Every update to existing canonical Markdown carries the observed content hash. Retryable
mutations carry an idempotency key. Stale writes fail closed and never overwrite concurrent
Obsidian edits.

## DD-039: Execution history is canonical; feedback is rebuildable

Explicit outcomes, corrections and reset preferences are canonical Markdown.
Statistics, forecasts, fit summaries and diagnoses are disposable derived state.

## DD-040: Adaptive planning is optional, bounded and baseline-visible

The baseline bounded planner remains stable. Adaptive mode is explicitly off,
shadow or active, and every changed decision includes its baseline comparison.

## DD-041: Missing evidence is not negative evidence

Silence remains unaccounted. Missing energy, motivation, duration or outcome
fields are unknown and cannot be converted into failure by feedback code.

## DD-042: Feedback may propose but never rewrite plans

Duration calibration and avoidance hypotheses can create reviewable proposals.
They cannot directly modify tasks, plans, goals or tracking routines.

## DD-043: Adaptive preferences are canonical and derived evidence is disposable

Mode, disabled dimensions, event exclusions, diagnosis dismissals, and reset
boundaries live in `system/adaptive-planning.yml`. Forecasts, diagnoses, replay
results, and normalized evidence caches live under `.lifeos/feedback/` and may be
deleted and rebuilt.

## DD-044: Historical replay forbids outcome leakage and universal scores

A replayed morning menu may use only evidence from dates strictly before that
planning day. Outcomes from the replayed day are evaluation data, not planning
input. Capacity overflow, unused time, completion, estimate error, missingness,
and explanation coverage remain separate measures.

## DD-045: Adaptive preference upgrades are explicit and conservative

Schema migration is previewable and never edits plans or execution history.
Legacy enabled feedback migrates to Shadow, unsupported schemas fail closed, and
upgrade failure leaves the original preference file byte-for-byte intact.

## DD-046: Feedback proposals reuse the consequential-change state machine

Adaptive evidence may create a draft proposal with exact evidence, alternatives,
confidence, target hash, and typed patch. It may not directly rewrite a plan.
Submission, approval, application, interruption recovery, and stale-target
handling remain identical to other proposals.

## DD-047: Goal readiness is deterministic and may result in no plan

The copilot checks explicit goal facts before model use. Missing information is
represented as unknown or a question. Clarify, experiment, link, park, pause,
decline, and no-plan are valid outcomes.

## DD-048: Goal-to-plan context is minimized, previewed, and explicitly scoped

Only bounded, traceable context is model-bound. Sensitive scopes require policy
permission plus explicit user inclusion. Redaction occurs before invocation.

## DD-049: Plan options are bounded alternatives, not automatic decisions

A session produces zero to three meaningfully different options. Assumptions,
tradeoffs, risks, missing evidence, and reasons an option may not fit remain
visible and editable.

## DD-050: Copilot decomposition uses rolling-wave depth

Only the current review wave becomes actionable tasks. Distant work remains as
coarse outcomes and is decomposed again from current canonical state after a
review or material change.

## DD-051: Copilot drafts reach Markdown only through proposals

Planning sessions, model output, option drafts, and UI state cannot directly
modify goals or plans. The final user-visible draft is converted into typed
proposal operations with stale-write validation and recovery.

## DD-052: Living replanning starts from current canonical state

A replanning review compares current goals, plans, execution evidence, explicit
corrections, and visible review answers. It never reapplies an old draft over a
newer source. Consequential outcomes create proposals, while continue unchanged
creates no proposal. Applied outcomes append inspectable decision lineage.

## DD-053: Model adapters are optional and provider-neutral

Core readiness, context, clarification, decomposition, capacity, explanation,
proposal, and replanning behavior remains deterministic. Adapters receive only
the previewed bounded request and must return the repository schema. Missing,
timed-out, or invalid adapters cannot block ordinary vault use.

## DD-054: Copilot runtime state is disposable

Planning sessions, workspace drafts, indexes, and replanning caches may be
deleted and rebuilt. Goals, plans, proposals, execution evidence, review notes,
and applied decision lineage remain ordinary canonical Markdown and are never
owned by disposable copilot state.
