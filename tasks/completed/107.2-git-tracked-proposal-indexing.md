# Objective
Rebuild the proposal-summary table from Git-tracked canonical proposal files.

# Dependencies
LIFEOS-107.1.

# Scope
Proposal discovery must use a Git-tracked-path provider.

The existing registry files table may be reused only if `register_scan()` is proven to contain Git-tracked files exclusively. Otherwise, LIFEOS-107.2 must introduce or reuse a narrow Git inventory abstraction that returns tracked canonical `proposal.md` paths.

Load proposals through the existing proposal loader (`load_proposal_directory`).

`ProposalMetadata` has no native `updated_at`. Define the helper as:
- collect non-null canonical lifecycle timestamps
- parse them using the existing proposal timestamp parser
- select the chronologically latest value
- serialize it using the existing canonical timestamp representation

Do not use filesystem time, Git commit time, scan time, or current time. Raw string comparison is permitted only if the existing schema guarantees one identical normalized timestamp format and that guarantee is covered by tests.

Load and validate the complete proposal set before modifying SQLite.
Refresh the table in one transaction:
```text
BEGIN
DELETE FROM proposals
bulk insert complete scanned set
COMMIT
```
On failure, rollback so previous proposal rows remain unchanged.
The scan must remove rows for proposals that are no longer Git-tracked and update rows whose canonical metadata changed.

# Non-goals
* incremental filesystem watchers
* partial refresh
* mutation of proposal files
* indexing untracked proposals
* silently skipping malformed tracked proposals

# Expected files
* `src/lifeos/registry/proposals.py`
* existing scanner integration module, when required
* `tests/registry/test_proposals_index.py`

# Acceptance criteria
* tracked canonical proposal is indexed
* untracked canonical-looking proposal is ignored
* tracked proposal removed from Git is removed after rescan
* title and lifecycle status changes are reflected
* derived `updated_at` is deterministic
* malformed tracked proposal aborts refresh
* failed refresh preserves the prior table contents
* repeated scan is idempotent
* scan writes no canonical files

# Focused test plan
* `tests/registry/test_proposals_index.py`: Verify that index population strictly matches Git-tracked proposals, that `updated_at` correctly resolves the latest chronological lifecycle event, and that removing a proposal from Git correctly drops it during the next transactional scan.
