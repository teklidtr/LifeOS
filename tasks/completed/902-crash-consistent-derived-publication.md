# Goal

Publish disposable graph views and export bundles as internally consistent
units, with recoverable behavior when a build fails partway through.

# Discovered issue

Graph builds currently publish `graph.json` and `state.json` as separate writes.
A failure between them can leave graph content and clean-state metadata from
different builds. Export directory swapping has backup and cleanup paths whose
post-publication failures can report total failure even though the new bundle
is already live, and interrupted cleanup can leave ambiguous directories.

# Scope

- Define a transaction layout under the applicable `.lifeos` runtime subtree.
- Build the complete output in an isolated staging directory.
- Validate all generated files and the manifest/state record before
  publication.
- Publish a complete generation through one deterministic pointer or directory
  switch that never exposes mixed generations.
- Record enough phase information to classify and recover interrupted builds.
- Make restart recovery idempotent.
- Distinguish pre-publication failure, successful publication with cleanup
  warning, and unresolved recovery state.
- Add deterministic fault-injection checkpoints around generation,
  verification, publication, pointer/state update, and cleanup.
- Preserve the disposable and rebuildable nature of graph and export outputs.

# Out of scope

- Full machine power-loss durability guarantees.
- Making graph or export output canonical.
- Continuous background synchronization.
- Uploading or publishing bundles outside the local runtime directory.
- Reusing the proposal recovery journal without a separate design review.

# Required invariants

- Readers never observe graph data and state metadata from different builds.
- Readers never observe an export manifest that names missing or old files.
- A failed pre-publication build leaves the prior generation usable.
- Cleanup failure after successful publication does not misreport the new
  generation as absent.
- Restart can deterministically finish cleanup or restore the prior generation.
- Repeated recovery is idempotent.

# Required tests

- Fault after graph payload write but before state publication.
- Fault after export staging validation but before publication.
- Fault immediately after publication but before cleanup.
- Corrupt or incomplete staging generation.
- Existing valid generation remains readable after failed replacement.
- Restart recovery for every persisted phase.
- Two consecutive identical builds remain deterministic.
- Concurrent build attempts are serialized or rejected explicitly.

# Acceptance criteria

- Graph and export consumers can identify one complete active generation.
- No ordinary interruption leaves a mixed active generation.
- Recovery behavior is explicit, deterministic, and tested.
- Status commands report active generation, unresolved recovery, and stale
  cleanup separately.
